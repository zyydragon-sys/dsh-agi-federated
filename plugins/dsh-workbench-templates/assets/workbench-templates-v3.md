GA 实测数据（借鉴依据）：
- 同等任务 token 消耗为主流智能体的 15%-35%
- 同任务 5 次重复：102s→66s，20 万→10 万 token（SOP 提炼复用）
- 跨任务重复执行 token 平均下降 79.3%，最高 92.4%
- 长期进化：同一任务首轮 22.2 万 token/32 次调用 → 第九轮 2.3 万/5 次
- 核心洞见：长周期性能的决定因素不是上下文长度，
  而是有限上下文预算内维持多少与决策相关的信息（信息密度）。

第一节  规模化架构：10-30+ Agent 的团队-of-团队（v3 新增）
===============================================================================

【1.1 三层指挥树】
-------------------------------------------------------------------------------
                    ┌─────────┐
                    │  Lead   │  只做：规划 DAG / 分片 / 验收 / 裁决
                    │(强模型) │  不做：任何具体执行
                    └────┬────┘
          ┌──────────────┼──────────────┐
     ┌────┴────┐    ┌────┴────┐    ┌────┴────┐
     │ SubLead │    │ SubLead │    │ SubLead │  各管一个分片(≤6 成员)
     │(中模型) │    │         │    │         │  汇总分片进度，初审交付
     └────┬────┘    └────┬────┘    └────┬────┘
        ┌─┴─┐        ┌─┴─┐        ┌─┴─┐
        成员×N        成员×N        成员×N      只做执行 + 标准报告
       (经济模型)    (经济模型)    (经济模型)
-------------------------------------------------------------------------------

规模守则：
- Lead 直接子节点 ≤4（SubLead 或独立专家如 evidence-collector）
- 每个 SubLead 分片成员 ≤6
- 理论上限 4×6=24 执行成员 + 4 SubLead + Lead ≈ 29 Agent
- 超过 24 执行成员 → 加第二棵指挥树，两树间只通过磁盘工件通信

【1.2 分片原则（何时切 SubLead）】
-------------------------------------------------------------------------------
满足任一条即分片：
- 同类任务 >3 个（如 5 个网站的抓取 → 1 个 SubLead + 5 工人）
- 任务需要共享上下文（同Repo不同模块）
- 工人用的模型比 Lead 弱，需要有人初审

分片命名：<领域>-squad（如 scrape-squad / build-squad / verify-squad）

【1.3 工件介质通信（10+ Agent 的生命线）】
-------------------------------------------------------------------------------
铁律：Agent 之间不传长消息，一切经过磁盘。
- 每个任务的产出 = 文件路径 + 一行状态（PASS/FAIL/BLOCKED）
- 汇总者只读文件，不读聊天历史
- SubLead 向 Lead 汇报 = 分片 summary.md 的路径 + 3 行以内结论
- Lead 的上下文里永远只有：任务板状态 + 各分片 3 行结论
  （这就是 30 人团队 Lead 上下文不爆炸的原因）

目录约定：
D:\Deepseek工作区\.team-work\
  ├─ squads\<squad名>\summary.md        ← SubLead 写，Lead 读
  ├─ tasks\<task-id>\report.json        ← 成员写（3.5 schema）
  ├─ tasks\<task-id>\artifacts\...      ← 交付物
  └─ conflicts\                          ← 跨分片冲突记录

【1.4 Lead/SubLead 分工表】
-------------------------------------------------------------------------------
职责                | Lead            | SubLead         | 成员
--------------------+-----------------+-----------------+----------
建团/改DAG/审批交互  | ✔               | ✗               | ✗
分片内派任务         | ✗               | ✔               | ✗

终审（质量门）       | ✔（转 evidence- | ✗               | ✗
                    | collector 独立验│                 |

冲突裁决             | ✔               | 上报             | 上报

第二节  Token 经济学：GA 四机制落地（v3 核心）
===============================================================================

【2.1 机制一：上下文信息密度最大化】
-------------------------------------------------------------------------------
原则：往每个 Agent 的上下文里放"决策相关"的信息，其余一律不给。

派任务时的密度检查（Lead 自查三问）：
1. 这条信息会改变成员的执行决策吗？不会 → 删。
2. 这段背景一句话能说清吗？能 → 压成一句话。
3. 成员需要时能自己查到吗（文件/命令）？能 → 只给路径。

反模式（禁止）：
- 把整个需求文档贴进任务描述（→ 只贴相关段落 + 文档路径）
- 把上游完整报告转给下游（→ 用 3.7 HANDOFF 块，≤10 行）
- 把历史对话当作上下文带给新成员（→ 新成员零历史，只读工件）

【2.2 机制二：最小原子工具集】
-------------------------------------------------------------------------------
借鉴图灵完备工具观：code_run 理论上可复制一切工具，但保留少量原子工具
是为了降低决策成本（每次工具选择都是 token 开销）。

成员工具白名单（默认 9 个原子能力，五类）：
  文件：ops_read_files / ops_grep / ops_glob
  执行：ops_bash（含 node/python 脚本 = 图灵完备兜底）
  结果：ops_result
  记忆：mem_read / mem_write（见 §3）
  人在回路：报告（send_message）

规则：
- 不给成员多余工具；能用一个 ops_bash 脚本完成的不拆成多次工具调用
- 工具调用合并：能一次读 3 个文件就不调 3 次
- Lead 派发时显式声明本任务需要的工具子集，其余不给

【2.3 机制三：SOP 自进化（越用越省）】
-------------------------------------------------------------------------------
第一次做某类任务 → 完成时必须提炼 SOP；第二次起 → 直接执行 SOP。

SOP 触发条件（在有意义的时间点提炼，不是每步都提炼）：
- 子目标完成时
- 从失败中恢复成功时
- 同类任务第二次被派发时

SOP 文件结构（存 D:\Deepseek工作区\.team-memory\sop\）：
-------------------------------------------------------------------------------
# SOP-<编号>: <任务类型名>
适用：<什么任务用这个>
前置：<环境/依赖检查，1-3 行命令>
步骤：<最少必要步骤，每步一行命令 + 一行期望>
验收：<验证命令 + 期望结果>
坑：<已踩过的坑，一行一条>        ← 从失败中提炼，最有价值的部分
历史：<使用次数 + 最近一次 token 消耗>   ← 用于度量 SOP 收益
-------------------------------------------------------------------------------
派发规则：Lead 派任务前先查 sop\ 目录有无匹配 SOP；
有 → 任务描述只写"执行 SOP-xx，参数：<差异部分>"（token 直降 80%+）；
执行完 → 成员在报告中标注"SOP 是否可复用/需更新"。

【2.4 机制四：上下文压缩门】
-------------------------------------------------------------------------------
四个粒度的裁剪，保证活跃上下文不随轮数线性增长：

1) 任务级：每个任务上下文预算上限（默认 ≤3000 token 任务描述），
   超了 Lead 必须先压缩再派发。
2) 汇报级：成员报告走 3.5 schema，禁止叙述性长文。
3) 轮次级：成员自己发现"上下文里有超过 2 轮前的大段工具输出"→
   主动总结成 3 行要点后继续（自我截断）。
4) 交接级：跨任务交接必须过 3.7 HANDOFF 压缩块，禁止原文转发。

【2.5 模型分层路由（补充机制）】
-------------------------------------------------------------------------------
角色           | 模型档位     | 理由
---------------+-------------+-------------------------------------------
Lead           | 强模型      | 规划/DAG/裁决是 token 密度最高的决策
SubLead        | 中模型      | 分片管理是结构化工作
执行成员        | 经济模型     | 按确定性步骤执行
evidence-      | 强模型      | 验收判断不可省
collector      |             |
审查/汇总       | 中模型      | 对照式检查
-------------------------------------------------------------------------------
> 只有用户明确要求全强模型时才整体升级。默认分层可省 50-70% 成本。

【2.6 Token 预算条（写进每个任务描述）】
-------------------------------------------------------------------------------
Budget: 本任务预期 ≤<N> 次工具调用 / ≤<M> token。
接近预算时：先完成最小可验收交付，剩余部分写进报告 next 字段。
-------------------------------------------------------------------------------

【3.1 记忆分层（借鉴 GA 分层按需记忆）】
-------------------------------------------------------------------------------
层    | 内容                 | 注入策略              | 存储
------+----------------------+-----------------------+----------------------
L0    | 元记忆（索引的索引）  | 每次任务默认注入       | MEMORY-INDEX.md 头部
元记忆| "团队会什么/有什么"   | ≤200 token，有界       |
------+----------------------+-----------------------+----------------------
L1    | 索引层：只记录存在性  | 默认注入，有界         | MEMORY-INDEX.md
索引  | 不记内容，只记"有"    | （LLM 即解码器：知道   |
      | "SOP-07 有 npm 坑"   | 存在后按需取 L2/L3）   |
------+----------------------+-----------------------+----------------------
L2    | 事实知识：环境/路径/  | 按需读取               | facts\*.md
事实  | 版本/账号约束/坑      |                       |
------+----------------------+-----------------------+----------------------
L3    | 程序知识：SOP/脚本/   | 按需读取               | sop\*.md / tools\
程序  | 可复用流程            |                       |
------+----------------------+-----------------------+----------------------
L4    | 原始轨迹：完整报告/   | 不注入、不向上传播     | traces\<日期>\
轨迹  | 命令日志/失败现场     | （只作追溯证据）       |
-------------------------------------------------------------------------------
关键设计：L1 永远有界（记录存在性而非内容），记忆增长不挤占
任务上下文 —— 这是 token 效率与长效记忆兼得的核心。

【3.2 磁盘持久化结构】
-------------------------------------------------------------------------------
D:\Deepseek工作区\.team-memory\
  ├─ MEMORY-INDEX.md      ← L0+L1，唯一默认注入物，≤150 行
  ├─ facts\               ← L2：env.md / paths.md / pitfalls.md / people.md
  ├─ sop\                 ← L3：SOP-01..N
  ├─ tools\               ← L3：可复用脚本（下载/校验/自检）
  └─ traces\              ← L4：按日期归档，30 天后可清理（需批准）
-------------------------------------------------------------------------------

MEMORY-INDEX.md 结构：
-------------------------------------------------------------------------------
# Team Memory Index（≤150 行，超出即触发整理）
## 环境（存在性）
- [L2/env] PowerShell 5.1 only; Node=D:\node-26\node.exe; TLS curl 不可用
- [L2/paths] npm cache 必须设 D:\Deepseek工作区\.npm-cache
## 已有 SOP（存在性）
- [L3/sop-07] Node 工具链便携安装（含 npm cache 坑）
- [L3/sop-11] chrome-headless-shell 下载与 CDP 自检
## 已知坑（存在性）
- [L2/pit-03] ConvertTo-Json 写中文路径必坏 → 用 Node utf8
## 开放问题
- [ ] <未解决的事，一行一条>
-------------------------------------------------------------------------------

【3.3 记忆写回协议（何时写、谁写、写哪层）】
-------------------------------------------------------------------------------
时机（显式整合点，禁止每步都写）：
1. 任务完成时 → 成员在报告 next 字段建议 1 条记忆
2. 从失败恢复时 → 强制写 1 条 pitfall（最有价值）
3. SOP 第二次命中时 → 更新 sop\ 历史行
4. SubLead 汇总时 → 汇总分片级事实（每分片 ≤3 条）

写入规则：
- L2 写"事实 + 证据路径"，L3 写"步骤 + 验收命令"，L4 只存原始物
- 每条记忆一行一行写，禁止大段粘贴（保 L1 有界）
- 冲突时：新事实标注 replaces: <旧条目>，不静默覆盖
- 写回由 SubLead 统一执行（成员只建议），防并发写坏索引

【3.4 记忆召回顺序（任务开始时）】
-------------------------------------------------------------------------------
1. 读 MEMORY-INDEX.md（L0+L1，默认已有）
2. 索引命中 → 按需读对应 facts/sop 文件（L2/L3）
3. 团队记忆无 → DSH dsh-memory / Hindsight（平台层）
4. 仍无 → 现场探索，完成后按 3.3 写回
禁止：跳过索引直接翻 traces\（L4 是证据不是知识）。

【3.5 记忆维护（防腐烂）】
-------------------------------------------------------------------------------
- 每 10 个任务或每周：SubLead 检查 L1 索引是否超 150 行，
  超了 → 合并同类、把低频条目降级到 L2/L3 详情文件
- 矛盾条目 → 以最新 traces 证据为准裁决，被替换条目删除
- 删除记忆必须先确认 traces\ 里有原始证据（可恢复原则）

【4.1 执行成员增量块】
-------------------------------------------------------------------------------
Token discipline:
- Read MEMORY-INDEX.md first. Follow index hits to facts/sop files only
  when needed. Do NOT browse traces/.
- If an SOP matches your task, execute the SOP with parameter diffs only.
- Merge tool calls; never read the same file twice; summarize any tool
  output over ~50 lines into ≤5 bullet points before moving on.
- Stay under your task budget: <N> tool calls / <M> tokens. Approaching
  budget → deliver the minimal acceptable artifact, note the rest in
  report.next.
- At completion, suggest ≤1 memory entry (fact / pitfall / SOP candidate)
  in report.next. Do not write memory files yourself.

(然后粘贴 v2 的 1.3 Mind-Virus 防线)
-------------------------------------------------------------------------------

【4.2 SubLead 增量块】
-------------------------------------------------------------------------------
You are SubLead of <squad 名>-squad. You manage ≤6 workers.

- Dispatch: give each worker only the task contract + tool whitelist +
  budget line. Never forward Lead's full plan.
- Collect: workers report via 3.5 schema to tasks\<id>\report.json.
  You read files, not chat history.
- First review: formality only (artifacts exist, schema complete).
  Quality gate belongs to evidence-collector, not you.
- Consolidate: write squads\<squad名>\summary.md with ≤10 lines:
  per-task one-line status + conflicts + squad verdict.
- Memory: at squad completion, write ≤3 fact entries and any pitfall
  from failed-and-recovered tasks into .team-memory (per 3.3 write-back
  protocol). You are the only writer in your squad.
- Escalate to Lead when: cross-squad conflict, budget blown >50%,
  or 2 workers BLOCKED on the same root cause.

(然后粘贴 v2 的 1.3 Mind-Virus 防线)
-------------------------------------------------------------------------------

【4.3 Lead 规划增量块】
-------------------------------------------------------------------------------
Before creating any team:
1. Check .team-memory\MEMORY-INDEX.md — reuse SOPs, avoid known pitfalls.
2. Single agent can do it? → no team (most expensive multi-agent system
   is the one that does not need to be multi-agent).
3. Scale plan: >12 workers → team-of-trees per §1.1; assign SubLeads;
   define squad boundaries and disjoint write paths BEFORE dispatch.
4. Model routing: Lead/verifier strong model; SubLeads mid; workers
   economy — unless user explicitly overrides.
5. For each task: attach budget line (2.6) + HANDOFF expectations (3.7).
6. After delivery: require evidence-collector verdict; then approve
   memory write-backs (SubLeads propose, you approve team-level facts).

(然后粘贴 v2 的 1.3 Mind-Virus 防线)
